**Détail P0 :**

- **C1 — Système de conditions** : livré dans `supabase/migrations/20260820000001_permission_conditions.sql` et `supabase/migrations/20260820000002_cancel_payment_condition.sql`.
  - `condition_type` enum créé.
  - Tables `permission_conditions`, `cash_registers`, `security_portals` créées.
  - RPC `has_condition(condition_type, params)` sécurisée contre les casts invalides.
  - `has_permission()` réécrit pour évaluer les conditions attachées aux grants ALLOW.
  - Conditions critiques raccordées :
    - `finance.payment.record` → RLS INSERT `fee_payments` avec `cash_register_open`.
    - `finance.payment.cancel` → RPC `cancel_payment()` avec `within_cancellation_window`.
    - `finance.control.scan` → RLS INSERT `fee_control_scans` avec `campaign_published`.
  - Écarts C1 restants : `security.scan` (lien `location_id`/`portal_id` absent), `security.pickup.manage` (table pickups inexistante), `pedagogy.grade.manage` (condition `grade_not_published` non dans l’enum), `email.send` (table outbox inexistante + quota).

- **C2 — Exceptions individuelles** : livré dans `supabase/migrations/20260820000003_profile_permission_exceptions.sql`.
  - Table `profile_permission_exceptions` créée avec `UNIQUE(profile_id, permission_code)`.
  - `has_permission()` réécrit avec la résolution complète :
    1. DENY de rôle → DENY.
    2. DENY d’exception active → DENY.
    3. ALLOW d’exception active → ALLOW.
    4. Sinon résultat des rôles (avec conditions C1).
  - Trigger d’audit `audit_profile_permission_exceptions` sur INSERT/UPDATE/DELETE.
  - Permissions de base RLS sur la nouvelle table (à compléter si des politiques spécifiques sont requises).
